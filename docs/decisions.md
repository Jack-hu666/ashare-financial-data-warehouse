# 关键设计决策记录

每条决策都回答「为什么这么做」，供面试讲解用。数字均为本次实现真实值。

---

## 决策 1：为什么「营业成本」弃用新浪、改用东财利润表

**这是本项目踩到的最关键的数据坑。**

- 起初用 `ak.stock_financial_abstract`（新浪财务摘要）取「营业成本」。
- 用贵州茅台核对时发现异常：算出的毛利率只有 **66.6%**，而茅台真实毛利率约 **91%**。
- 逐字段排查发现：新浪该接口的「营业成本」字段，实际值是**「营业总成本」**（含税金及附加、期间费用等），不是利润表里的「营业成本（COGS）」。
  - 茅台 2024：新浪「营业成本」= 545.2 亿；东财 `OPERATE_COST`（真 COGS）= 137.9 亿。
  - 用真 COGS 算：毛利率 = (1741.4 - 137.9) / 1741.4 ≈ **92.1%**，与新浪自带「毛利率」字段 91.93% 吻合。
- 结论：统一改用**东财三大报表接口**（利润表 / 资产负债表 / 现金流量表），口径一致、字段命名规范。
- **教训**：字段名≠字段含义，任何口径都要拿一两家自己熟悉的公司手工核对一遍再信。

## 决策 2：为什么缺失值不补 0

- 补 0 会让比率指标严重失真：`gross_margin = (revenue - cost)/revenue`，若 cost 缺失补 0，毛利率会虚高到 100%；若 revenue 补 0，分母为 0 直接崩。
- 本项目缺失的 `ar`（应收账款）集中在**银行、券商**（金融企业报表本就没有应收账款，是贷款/金融资产），补 0 会凭空造出「0 应收账款」的假数据。
- 做法：全链路保留 NULL，指标计算用 `NULLIF(col, 0)` 做分母保护，聚合用 `AVG` 天然跳过 NULL。

## 决策 3：为什么 ST 股保留而不剔除

- **样本不失真**：剔除 ST 会让行业均值被系统性抬高（差的公司被删了），分析结果偏向幸存者。
- **打标比删除信息更多**：保留记录并打 `is_st` 标记，下游既能「看整体」也能「只看正常公司」，主动权留给使用者。
- 本次样本为 64 家大型蓝筹，实际无 ST 公司（`is_st` 全部为 False），但打标逻辑已按名称含 ST 实现，未来换样本即生效。

## 决策 4：为什么需要 DWD 层，不能直接从 ODS 算 DWS

- **复用性**：单位统一、日期对齐、主键去重、ST 打标这些事做一次，DWS 的所有指标、ADS 的所有表都直接复用，不必每张表重复清洗。
- **口径统一**：如果每个指标脚本各自从 ODS 清洗，同一字段可能出现两种口径，排查成本极高。
- **可追溯**：ODS 保持原始、DWD 是「干净明细」，出问题时能分清「源数据脏」还是「清洗逻辑错」。
- **性能**：清洗后的 DWD 分区紧凑（Parquet + 按 report_date 分区），比每次扫原始宽表快。

## 决策 5：金额单位是怎么核对和处理的

- 需求要求把金额统一成「元」。
- 核对过程：拿浦发银行 2025 年报营收（真实约 1739.6 亿元）比对采集值 `1.73964e11`（元），完全一致；茅台总资产约 3000 亿对上 `3.0e11` 元。**确认东财接口原始单位就是「元」**。
- 处理：`dwd_clean.py` 里保留 `UNIT_SCALE = {元:1, 万元:1e4, 亿元:1e8}` 的换算结构，当前源单位为元、倍率 1，即「核对后无需换算」。若换接口出现万元/亿元，只改一处 `SOURCE_UNIT` 即可整体换算。

## 决策 6：为什么 Spark 用 local[*] + Java 17 + winutils（环境）

- `local[*]`：约束要求单机演示，不搭集群；数据量 768 行，单机秒级。
- **Java 17**：PySpark 4.1.1（Spark 4.x）要求 Java 17，且必须含 `jdk.incubator.vector` 模块。PyCharm 自带的精简 JBR 缺该模块跑不起来，故装完整 Temurin JDK 17。
- **winutils.exe + hadoop.dll**：Windows 上 Hadoop 本地文件系统（读 Parquet、建临时目录）依赖这两个原生文件，放在 `HADOOP_HOME/bin`，并通过 `-Djava.library.path` 指向它。

## 决策 7：为什么写 MySQL 用 pandas + SQLAlchemy，而不是 Spark JDBC

- Spark 原生 `df.write.jdbc` 需要额外下载 `mysql-connector-j` 的 JAR 并管理驱动。
- 本项目结果表都很小（公司级 768 行、行业级 348 行），`toPandas()` 拉回驱动端再 `to_sql` 没有任何性能问题，且免去 JAR 依赖，链路更简单。
- 建表结构仍由 `sql/ddl.sql` 统一控制（`DECIMAL`、主键），`to_sql` 只负责灌数据。

## 决策 8：应收账款周转率口径

- 公式取 `revenue / avg(ar)`，其中 `avg(ar)` 定义为**近 4 期（含当期）窗口均值**，近似「年平均应收账款」。
- 金融企业 `ar` 为 NULL，该指标自然为 NULL，不参与行业均值，避免被 0 或异常值污染。
